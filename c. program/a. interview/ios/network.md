## tCP建立连接三次握手的过程

- TCP三次握手指的是客户端与服务器之间至少要发送三个数据包从而建立TCP连接的过程

         +------------+                      +------------+
         |   Client   |                      |   Server   |
         +------------+                      +------------+
               |                                    |
               |                                    |
               |         SYN = 1 & seq = J          |
      SYN_SENT | -------------------------------->  |
               |                                    |
               |                                    |
               |                                    |
               |       ACK = 1 & ack = J + 1        |
               | <--------------------------------  | SYN_RECV
               |        SYN = 1 & seq = K           |
               |                                    |
               |                                    |
               |                                    |
               |       ACK = 1 & ack = K + 1        |
   ESTABLISHED | -------------------------------->  |
               |                                    |
               |                                    |

- 第一次握手: 客户端向服务器发送请求数据包,发送后进入SYN_SENT状态,
              数据包包含标志位SYN值为1和随机序列号seq,这里假设seq值为J;

- 第二次握手: 服务器向客户端发送确认数据包,发送后进入SYN_RECV状态,
              数据包包含标志位ACK值为1和确认序列号ack值为J+1,
              以及标志位SYN值为1和随机序列号seq,这里假设seq值为K;

- 第三次握手: 客户端向服务器发送确认数据包,发送后进入ESTABLISHED状态,
              数据包包含标志位ACK值为1和确认序列号ack值为K+1,
              当服务器接收到确认数据包后也进入ESTABLISHED状态到此TCP握手结束;

## 为什么TCP是三次握手,不是一次、两次或者四次

- 一次握手:客户端向服务器发送了一个请求数据包就建立连接是不太可能的,因为客户端连服务器的真实性都无法确定;
- 二次握手:客户端向服务器发送了一个请求数据包但由于网络原因过了一段时间后服务器才收到并返回确认数据包,而客户端由于超时会丢掉这个确认数据包;因为是两次握手服务器此时会进入ESTABLISHED状态等待客户端传输数据从而导致了服务器资源浪费;
- 四次握手:最开始本来是四次握手服务器发送的SYN和ACK是分开发送的,后面优化后变成了三次握手;

## tCP终止连接四次挥手的过程

         +------------+                      +------------+
         |   Client   |                      |   Server   |
         +------------+                      +------------+
               |                                    |
               |                                    |
               |         FIN = 1 & seq = M          |
   FIN_WAIT_1  | -------------------------------->  |
               |                                    |
               |                                    |
               |                                    |
               |                                    |
               |        ACK = 1 & ack = M + 1       |
   FIN_WAIT_2  | <--------------------------------  | CLOSE_WAIT
               |                                    |
               |                                    |
               |                                    |
               |                                    |
               |         FIN = 1 & seq = N          |
               | <--------------------------------  | LAST_ACK
               |                                    |
               |                                    |
               |                                    |
               |                                    |
               |         ACK = 1 & ack = N + 1      |
   TIME_WAIT   | -------------------------------->  | CLOSED
               |                                    |
               |                                    |

- 第一次挥手: 客户端向服务器发送请求数据包,发送后进入FIN_WAIT_1状态,
              数据包包含标志位FIN为1和随机序列号seq,这里假设seq值为M;

- 第二次挥手: 服务器向客户端发送确认数据包,发送后进入CLOSE_WAIT状态,
              数据包包含标志位ACK值为1和确认序列号ack值为M+1,
              客户端接收到该数据包后进入FIN_WAIT_2状态;

- 第三次挥手: 服务器准备好关闭连接后向客户端发送请求数据包,发送后进入LAST_ACK状态,
              数据包包括标志位FIN为1和随机序列码seq,这里假设seq值为N;

- 第四次挥手: 客户端向服务器发送确认数据包,在发送后进入TIME_WAIT状态,
              数据包包含标志位ACK为1和确认序列号ack值为N+1,
              服务器收到数据包后进入CLOSED状态,客户端等待2MSL如果没有收到回复就会关闭连接;
              (MSL是指一个TCP报文段在网络中的最长存活时间)

## tCP和UDP的区别

- TCP主要通过确认和重传机制、数据合理分片和排序、数据校验机制、拥塞控制和流量控制提供了一种面向连接的、面向字节流的可靠通信服务,
  同时也保证了数据的顺序和无边界性,另外TCP报头至少20个字节而且一对一;

- UDP提供了一种面向无连接的、面向报文段的不可靠通信服务,容易丢包但是速度快,
  不能保证数据顺序而且数据有边界,另外UDP报头8个字节可以一对一也可以一对多;

## hTTPS加密过程

         client                                                                 server
+--------------------------+                                           +---------------------------+
|                          |              发送一个HTTPS请求            |                           |
|                          | ----------------------------------------> |  +-------------------+    |
|                          |                                           |  |      证书公钥     |    |
|  +--------------------+  |                                           |  |      证书私钥     |    |
|  |  验证证书是否有效  |  | <---------------------------------------- |  +-------------------+    |
|  +--------------------+  |                返回证书公钥               |                           |
|            |             |                                           |                           |
|            | yes         |                                           |                           |
|            v             |                                           |                           |
|  +--------------------+  |                                           |                           |
|  | 本地生成一个随机值 |  |                                           |                           |
|  +--------------------+  |                                           |                           |
|            |             |                                           |                           |
|            |             |                                           |                           |
|            v             |                                           |                           |
|  +--------------------+  |      将刚才加密后的密钥发送给服务端       |  +-------------------+    |
|  | 证书公钥加密随机值 |  | ----------------------------------------> |  | 用私钥解密获取秘钥|    |
|  +--------------------+  |                                           |  +-------------------+    |
|            |             |                                           |                           |
|            |             |                                           |                           |
|            v             |                                           |                           |
|  +-------------------+   |                                           |  +----------------------+ |
|  |     秘钥解密信息  |   | <---------------------------------------- |  |用秘钥加密要发送的内容| |
|  +-------------------+   |              将加密的内容发送给客户端     |  +----------------------+ |
|                          |                                           |                           |
|                          |                                           |                           |
+--------------------------+                                           +---------------------------+

- 客户端向服务器发送一条HTTPS消息,其中包含了客户端的TSL协议版本、可供选择的压缩和加密算法;
  服务器接收到后会向客户端发送消息,其中包含了服务器端的TSL协议版本、所选择的压缩和加密算法、以及带公钥的CA证书;

- 客户端根据本地信任的CA列表验证证书是否可信, 认为可信后会在本地生成伪随机数并通过服务器的公钥加密后发送给服务器;
  服务器通过私钥解密后获得该随机数并将其作为后续对称加密的密钥,至此客户端和服务器开始使用对称加密传输所有数据;

- 常见非对称加密算法: RSA、ECC
  常见对称加密算法: DES、AES
  散列函数算法: MD5、SHA

## hTTP1.0 、 HTTP1.1与HTTP2

```text
- 1.1新增了持久连接 & 管道化传输 & 缓存机制优化;
  持久连接是指在一个TCP连接上就可以进行多个HTTP请求和响应;
  管线化传输是指发送当前请求不再依赖上一个响应是否结束,但响应的顺序依旧遵照FIFO的方式(也就是队头阻塞问题);
  缓存机制优化是指引入了Etag和Cache-Control等更为高效的缓存机制;

- 2.0新增了头部压缩 & 二进制格式 & 多路复用技术 & 服务器推送;
  头部压缩是指将重复的头部字段进行编码和压缩,并且通讯双方各自建立header field缓存表从而减少重复header的传输;
  二进制格式是指采用帧为最小数据单位并合成数据流进行传输,解决之前基于文本传输不可切割的痛点;
  多路复用是指是的在一个TCP连接中可以同时进行多个请求和响应且不用按照顺序,解决HTTP协议层面的队头阻塞问题;
  服务器推送是指服务器可以主动向客户端发消息;

```
